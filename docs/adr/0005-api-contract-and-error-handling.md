# 0005-api-contract-and-error-handling

## 上下文
系统需要对外暴露稳定的 RESTful 接口，并向客户端提供明确的 HTTP 状态码与业务错误码体系；同时需保障规则同步的高严谨性与审计日志的有效性。

## 决策
1. **HTTP 状态码与业务错误码分工**：
   - HTTP 状态码反映传输层语义：400（参数校验失败）、404（资源不存在）、409（资源冲突，如 Key 冲突或优先级冲突）、500（服务器内部异常）。
   - 响应体统一封装 `{ "code": "<BUSINESS_CODE>", "message": "<HUMAN_MESSAGE>", "data": <PAYLOAD> }`。
   - 业务错误码采用全大写字符串常量：`VALIDATION_ERROR`、`FLAG_NOT_FOUND`、`FLAG_KEY_CONFLICT`、`PRIORITY_CONFLICT`、`INTERNAL_ERROR`。
2. **规则同步防重与归属校验**：
   - `PUT /api/v1/flags/:id/rules` 必须校验传入的规则 ID 是否全量归属于当前 Flag，严禁跨 Flag 篡改规则 ID。
   - 校验规则列表内禁止存在重复 ID、禁止存在重复优先级。
   - 在比对完成后，若规则内容和排序完全无变动（新增、修改、删除明细均为空），则静默跳过审计日志写入，不生成无意义的空白审计。
3. **环境与部署幂等性**：
   - 数据迁移脚本具备严格幂等性，启动检测机制保证已完成的迁移不会重复应用。
   - 初始化演示数据采用 `ON CONFLICT DO NOTHING` 或条件校验，保证重启时不重复插入。

## 原因与权衡
明确的业务错误码与 HTTP 状态码组合便于前端精确处理冲突；归属校验与空白审计抑制确保了系统的严密性与审计流的高信噪比。
